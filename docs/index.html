What the app is

VENOM Router (called Upstream Checker until this month) is a Windows desktop app that holds API keys for many model providers and sends requests through whichever key and model the owner picks. It tests keys, tracks quotas, benchmarks models and keeps a history of runs. One person uses it, on their own data, every day.

The problem Phase 2 fixes

Everything was stored in flat JSON files that the renderer read and wrote through IPC. An audit found six ways that lost data. The worst: if reading config.json failed for any reason — a corrupt file, antivirus holding a lock, a zero-byte file after a power cut — the app treated it as an empty config, seeded the default providers and wrote them back, destroying every stored key. Closing the window did the same thing a second way. On top of that, two IPC calls doing read-modify-write lost concurrent updates, the 300 KB catalogue was rewritten whole on every sync, write failures were silent, and keys were decrypted on every read and handed to the renderer in plain text.

Key ideas

Two databases, not one. venom.db holds configuration, the catalogue, keys and run history. venom-logs.db holds the request log. They are separate so that a log that grows to gigabytes, or fails to open at all, never puts the app's real data at risk — if the log database will not open, logging switches off and the app carries on.

Placeholders instead of secrets. The renderer never receives a key. It receives a placeholder string and a display hint like the last four characters. When a request goes out, the main process swaps the placeholder for the real secret, and only if the request's origin matches the key's own. The log then records which placeholder was used, never the secret.

Raw rows and roll-ups. Every request writes a row. In parallel, counters are folded into an hourly summary table. Charts read the summaries, which stay cheap for ever; detail views read the rows, which are purged after 90 days. Bodies are the most expensive and the most sensitive part, so only failed requests keep one, for seven days.

One ending per request. A request can finish by completing, timing out, being cancelled mid-stream, or having its connection dropped — and more than one of those can fire. The requester was rewritten so exactly one of them wins and exactly one log row is written.

Approach

Phase 2 was split into three sub-projects rather than built as one change, because each one has a different risk. A is a storage migration on live data — the dangerous part, done first and alone so it could be verified against real files before anything was layered on it. B is additive: a new database, a new writer, new channels, and an app that still works if the whole thing fails to start. C is user interface over an API that already exists and is already tested.

Each sub-project got its own design spec, its own plan with one commit per task, and its own branch in a separate worktree, so the owner's checkout stays on main and stays runnable while work is in flight.

Why B and C merge together

Shipping the logging system alone would put a database, a background writer and a purge scheduler into the app with no way for the owner to see any of it — cost with no benefit, and a new failure surface no one would notice. Holding B until C is ready also means C's real needs can still change B's query API, which is exactly what happened: three gaps in that API only became visible once the pages were thought through.

⚠ The honest caveat

The logging system is proven by 268 tests and one scripted live check — not by use. It has never run for a week against the owner's real traffic, which is where a batched writer, an hourly roll-up and a purge scheduler usually reveal their problems. The gate that holds it for the log pages is also, by accident, the thing preventing that soak. Running the branch day to day while C is being written would buy real confidence cheaply.

Open questions

  • Does the Request Log replace Test History outright, or sit beside it? The plan puts it in that slot, but run history and request log are not the same thing.
  • Are the retention defaults right for one person's real usage — 90 days of rows, 7 days of failed bodies, 12 months of roll-ups — or should the log keep more and the bodies less?
  • Does Monitoring need a live tail, or is that only a Request Log feature?
  • Do the three query-API gaps go onto the logging branch before C, or after? Open, and the first thing C's spec has to settle.

Why is finished, tested work sitting unmerged?

Because on its own it would ship a database, a background writer and a purge scheduler with nothing in the app that reads them. The owner decided the logging system and the pages that display it reach users in the same release. That decision is also why three gaps in the query API were caught before they shipped rather than after.

Why SQLite instead of fixing the JSON files?

Most of the data loss came from the shape of flat files, not from bugs on top of them: whole-file rewrites, read-modify-write across two IPC calls, and a failed read that is indistinguishable from an empty file. Transactions and a schema remove the whole class. The engine is pinned and runs only in the main process.

Why do the keys stay in the main process?

So a renderer bug, an extension or a stray log line cannot leak one. The renderer works with placeholders; the main process substitutes the real secret per request, and only when the request's origin matches the key's own. Opaque-origin matches are refused outright.

Why not release the rebrand now and the rest later?

The rebrand moves the app's data folder. Shipping that alone, then shipping a storage migration a week later, gives every install two risky upgrades instead of one. They ride together, behind one smoke-tested build.

What does done look like?

One published version in which the owner opens the app, clicks Request Log, sees every request the app has made with its cost and timing, filters to the failures, reads a scrubbed body, and adjusts how long any of it is kept — on a data folder that has survived the move from the old name with every key intact.
